DeepSeek Harness（dsh）全景调研报告

调研主题：DeepSeek Harness 是什么 · 安卓本机安装可行性 · 与在用 Harness 的协同方案
调研日期：2026-08-17
调研方式：联网检索（官方仓库 / 官方文档 / 社区评测）+ 本机实测（Termux 环境逐项验证）
报告版本：v1.0

一、调研背景：需求与问题链 #

用户当前的 AI 工作底座是一套运行在安卓手机 Termux 环境中的开源 Agent Harness（Hermes），日常用于：多平台消息中枢、生活档案管理、工作流自动化、定时任务、知识库检索等。本次调研由以下问题链驱动：

1. DeepSeek Harness（下称 dsh）是什么项目？

2. 能否安装到安卓手机本机？可行性如何？

3. 它有没有适配手机的 Web UI？

4. 界面风格是否与在用的 Harness WebUI 接近？

5. 安装方式选哪种最优（AI 代装 / 电脑 USB / 手动 Linux）？

6. 安装后与在用 Harness 的使用差异、优缺点、必要性、想象空间？

7. 它能否当个人助理？门槛在哪？记忆系统与在用 Harness、OpenClaw 相比如何？

8. 安装后，在用的 Harness 能否调度它（含 A2A 等工具），实现"用户 → 主 Harness → dsh → 执行 → 回传 → 报告"的链路？

核心痛点（调研要解开的）：

  • 现有工作流的重活（批量代码、网页迭代）消耗主力模型配额，想找廉价执行引擎分流；
  • 需要证据级过程留痕的任务，聊天记录式日志证明力不足；
  • 想知道"第二个 Harness"是替代品还是工具件——值不值得装、装了怎么用。

二、项目档案：dsh 是什么 #

项内容
本体DeepSeek Harness，命令名 dsh，深度求索官方开源智能体框架（Agent Harness）

三、本机安装可行性：实测结论（可行，条件全绿） #

调研在目标安卓手机（Android 16，Termux 环境）上逐项实测：

检查项dsh 官方要求本机实测判定
Node.js^22.19.0 或 >=24.0.0v24.17.0 已在位✅ 零改动
架构linux-arm64aarch64，官方有 arm64 预编译件✅
Landlock 沙箱Linux 内核特性内核 6.12.58，syscall 实测 ABI 版本 6✅ 原生支持
依赖编译—主依赖树纯 JS，npm registry 直连正常✅ 无原生编译坑
内存 / 磁盘—14GB 内存（可用 6.5GB）/ 763GB 空闲✅
npm 包真实性—@deepseek-ai/dsh@0.1.0-rc.6 元数据实拉确认✅

执行沙箱验证（AI 代装路线的关键疑虑）：

  • AI 终端与手机系统同网络命名空间（实测 net:[4026531840] = 系统主 ns）；
  • 终端内 curl 127.0.0.1:8787（在用 Harness WebUI）→ HTTP 200，1ms 连接；
  • 结论：AI 代装无沙箱障碍，起本地端口服务手机浏览器可达。

唯一硬前置：一枚 DeepSeek 官方 API Key（platform.deepseek.com 申请）。模型绑定 DeepSeek API（预览版多 provider 路径未开放文档）。

安装方式对比结论：AI 代装（最优，环境已勘测）＞手动 Termux（可行但无必要）＞电脑 USB 调试（纯绕路——dsh 不是 APK，adb shell 终点仍是同样命令）。

四、Web UI 与移动端适配 #

  • 官方无手机 App，只有 Web UI + 命令行两种形态；
  • Web UI 为桌面优先设计：窄于 1024px 时侧边栏自动收窄，手机上展开抽屉会挤压主内容区（社区反馈"适配的不是很好"）；
  • 手机浏览器直接访问 127.0.0.1:3080 基础可用；
  • 社区移动适配插件已成熟涌现：TecFancy/dsh-mobile、mexiaosqwq/dsh-web-mobile（窄屏侧栏变 overlay 抽屉）、zhu1090093659/dsh-web-ui（皮肤中心+移动远程）等；
  • 界面风格：与在用的"本地端口 + 浏览器壳 + 会话流"同族——侧栏会话列表、中间对话流、底部输入框、过程留痕页。默认偏极简"毛坯"风，可装皮肤插件精装修。

五、与在用 Harness（Hermes）对比：差异、优缺点、必要性 #

5.1 五个本质差异 #

维度在用 Harness（Hermes）dsh
定位全场景管家：消息中枢+档案+工作流+定时任务开发者工作台：把一件事做完交付
触达通道多平台 IM + WebUI + 眼镜端 + A2A，主动找用户仅浏览器开 3080，用户找它
记忆人格持久记忆每轮注入 + 灵魂文件人格无用户画像记忆，persona 仅一个字符串
沉淀深度上百个为用户定制的 skill（档案库、FTS5 检索、笔记镜像、发布流水线等）生态爆发但全是通用件
模型绑定自有模型调度链默认绑死 DeepSeek API

5.2 dsh 客观优点 #

1. 过程透明杀手级：轨迹页摊开系统提示词、思维链、每次工具调用与返回——"真查了还是脑补了"可对质（Hacker News 上被称 killer feature）；

2. 账目透明：每会话实时统计步数、耗时、token、缓存命中率；配合 V4-Flash 低价，性价比可视化；

3. UI 想象空间：连前端都能整个换掉，皮肤/布局自由度极高；

4. 迭代速度：一夜 5 万星、三天千插件的生态势能；

5. 沙箱严格：Landlock 文件隔离 + 审批姿态系统，制度性防护更厚。

5.3 dsh 客观缺点（对本文用户场景） #

1. rc 毛坯，破坏性变更在路上；

2. 用户核心场景（生活档案、专业数据库、笔记镜像、IM 推送、眼镜端）那边全是空白，迁移成本远高于收益；

3. 无跨会话记忆，不"认识"用户；

4. 窄屏二等公民（需插件缓解）、无语音、无多端定时送达；

5. token 消耗偏重（第三方对比：同任务消耗约为另一开源 harness Pi 的 3 倍）。

5.4 必要性判定：不高，但有三个真实价值 #

① 尝鲜与视野；② DeepSeek 廉价算力的专用入口；③ 参照系（用它的轨迹页与计量反哺主 Harness 的改进）。定位应是"第二工作台/子引擎"，不是替代品。

六、记忆系统三方对比（dsh vs Hermes vs OpenClaw） #

记忆维度HermesOpenClaw（小龙虾）dsh
记忆载体memory + user profile 双库每轮注入纯 Markdown（USER.md / MEMORY.md / 每日 notes），无隐藏状态append-only 会话事件流（记"过程"非"认识你"）
用户画像有，深度定制有（指令式 + 生效/废止元数据）无内建
长期固化手动策展Dreaming 后台自动提炼晋升（打分门槛+去重+人可审阅）——目前最自动化的实现无内建，靠社区插件（auto-memory / Mnemon / Nowledge / Hindsight，发布均不足一周）
跨会话检索FTS5 会话库memory_search 混合检索（向量+关键词）tool-session-query（模型可翻查历史，但不自动想起）
迁移性—官方支持直接导入 Hermes 的 MEMORY.md/USER.md插件各搞各的，无标准

结论：记忆能力 OpenClaw ＞ Hermes ＞ dsh。dsh 哲学是"过程留痕"而非"认识主人"；要长期记忆必须装极早期社区插件，等生态稳定估计还需一两个月。

七、能否当个人助理：判定与门槛 #

判定：架构上能（一切皆插件，缺啥装啥），今天体验上是半成品助理。

#门槛严重度
1无跨会话用户记忆🔴 高
2无消息通道（不能主动推送，仅浏览器）🔴 高
3API Key 硬前置🟡 中
4rc 版破坏性变更风险🟡 中
5窄屏/无语音/定时任务弱🟡 中
6中文能力（本土模型，术语误解率低）🟢 无门槛

个人助理赛道的正经选手是 OpenClaw（记忆系统完善 + 多端通道），dsh 的本命是开发者工作台。

八、主 Harness 调度 dsh：链路设计与证据链 #

总判定：能。两条官方通道 + 一条 CLI 通道，全部实证。

通道形态证据状态
① Python SDK（deepseek-harness 0.2.0）with DeepSeekHarness(config): h.run("任务") → final_response；API Key 走环境变量注入子进程✅ PyPI 实拉确认
② ACP 桥（@deepseek-ai/dsh-acp 0.0.1-rc.1）开放标准 Agent Client Protocol：session/new → prompt → update 流式回传，含审批回调✅ npm 实拉确认
③ headless CLIdsh --profile headless "任务" 一次性执行，打印答案退出✅ 官方文档
④ A2Adsh 官方不带 A2A 协议支持，社区桥接件尚未成熟⚠️ 暂不可用

推荐链路（Python SDK 为主干）：

用户（IM 或 WebUI）
   → 主 Harness 解析意图 → Python SDK 拉起 dsh 子进程（stdio JSON-RPC）
   → dsh 在 Landlock 沙箱内执行（Bash/文件/搜索，全程留痕）
   → RunResult(final_response, events, notifications) 回流
   → 主 Harness 摘要 + 轨迹要点 → 呈报用户

选 SDK 而非 ACP 的理由：SDK 通知流含 subagent.started/finished（可观测其内部子代理），Python 为主 Harness 母语，出错可直接读 stderr 尾部 400 行排障。ACP 的已知限制：仅新会话、仅基线文本输入、仅已提交回答、连接级生命周期。

已探明的小坑：TS SDK 文档示例引用的 dsh-jsonrpc-agent 子进程命令在 npm 为 404（实测），该入口仅存在于源码仓库场景；Python SDK 自管子进程拉起，不受影响。

九、方案总结：三步走 #

第一步（装）：npm install -g @deepseek-ai/dsh → 后台启动 dsh web → 验证 3080 端口 → 装移动适配插件（TecFancy/dsh-mobile 或同类）→ 用户配置 API Key 后浏览器即用。

第二步（联）：pip 装 deepseek-harness Python SDK → 主 Harness 写"调度脚本"封装成 skill（固定版本号防 rc 漂移）→ IM 一句话即可驱动 dsh 执行并回传。

第三步（养）：轻任务分流给 dsh（V4-Flash 廉价算力）；重活/精细活留在主 Harness；观察记忆插件生态，待 Mnemon/auto-memory 类插件稳定后再决定是否给 dsh 补长期记忆。

回退预案：web 起不来 → headless 模式；适配插件冲突 → 回官方裸 UI；npm 源慢 → npmmirror 镜像；SDK API 变 → 封装层单点修复。

十、风险声明 #

1. 本报告基于 2026-08-17 时点信息，dsh 处于高速迭代期（rc.6 → rc.7 同日发布），具体 API/行为可能快速过时；

2. token 消耗数据来自第三方对比（Composio 对照测试：同模型不同 harness 任务完成率差三成；Pi 对比：token 消耗差三倍），非官方基准；

3. 社区插件的成熟度与安全均未审计，安装前需自行评估；

4. 本报告已在发布前移除一切真实人名/单位/地名信息（内容自脱敏）。
